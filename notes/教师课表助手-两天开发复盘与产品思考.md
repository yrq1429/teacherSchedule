# 两天做出教师课表助手：一次从真实工作出发的 AI 开发实践

> 整理日期：2026 年 10 月 13 日。依据：原开发笔记与当前项目源码。开发时长、导入数量和试用体验来自原记录；功能判断来自源码静态阅读，未验证云端部署与真机运行。本文新增的产品想法均为建议。

## 1. 我做的其实是一条教师工作流程

这个项目叫“教师课表助手”，使用微信原生小程序与微信云开发，由 WorkBuddy 辅助完成开发。

它起点很具体：机构发来一张混着很多老师课程的 Excel，老师要找自己的课、记住上课时间、课后给家长写反馈，月底再数课时。这些事情本身不复杂，却每天重复，而且信息散落在表格、聊天和记忆里。

项目把它们串了起来：

**拿到课表 → 提取自己的课程 → 按日期查看 → 上课打卡 → 写课后反馈 → 查历史与统计课时。**

这条链路比单独的日历或 AI 文案功能更有价值：一次录入的信息，可以继续服务于上课、沟通和月底回顾。AI 的角色也很明确：WorkBuddy 帮助开发；小程序里的模型帮助识别图片、润色表达；教师仍然负责事实和最终判断。

## 2. 当前版本已经实现什么

| 环节 | 源码中的能力 | 当前边界 |
| --- | --- | --- |
| 课程录入 | 手动新增、文本解析、Excel 导入、图片识别入口 | 图片识别依赖模型配置与实际识别效果；不是任意课表都能准确解析 |
| Excel 解析 | 机构总表按姓名关键词筛选、个人课表整表解析，识别星期、日期与时间块 | 规则围绕特定表格结构，遇到新机构模板仍需验证 |
| 导入预览 | 展示解析结果、删除不需要的行、批量导入 | 建议增加逐字段修正、冲突提示与批次撤销 |
| 导入去重 | 根据日期或星期、开始时间、课程名跳过重复项 | 时间或名称变化可能成为新记录，不能替代调课处理 |
| 课表查看 | 按日期与周浏览，支持固定星期课程和指定日期课程 | 固定模板与某次实际授课仍有进一步拆分空间 |
| 上课记录 | 按课程与日期记录打卡，统计实际课时 | “已打卡”代表教师记录，不等于机构核算已确认 |
| 课后反馈 | 关联课程和上课日期，保留原文与润色结果，支持 Kimi / 豆包选择 | 反馈编辑页目前主要提供英语、物理两种角色 |
| 历史检索 | 根据课程名、原文和润色内容检索，按本周、本月筛选 | 学员名依赖课程名称中的文字，目前不是独立学员档案 |
| 订阅提醒 | 定时检查次日课程，有课才尝试发送消息 | 实际触发时区、模板、授权与送达需要云端验证 |
| 数据统计 | 每周固定课程模板数量与时长、本月打卡数量和时长、反馈数量 | 每周模板统计不包含指定日期课程，界面应解释口径 |

原记录写到两天内完成了批量导入，并提到 13、102 与 115 的课程数量。这些数字适合记录当时的验证过程，不应当被写成所有表格的识别保证。

## 3. 为什么这个技术方案适合起步

前端负责页面、课程选择与预览，云函数负责 Excel 解析、批量入库、模型调用和提醒，数据库保存课程、打卡、反馈与订阅记录。

对于一个先解决自己问题的工具，这种方案减少了自建服务器的运维负担，也让需求到可用页面的距离变短。模型调用集中在云端，便于统一管理凭证、超时与错误处理。

但“通过云函数调用”是技术架构选择，不能直接推导为主体资质、平台审核或数据处理要求已经满足。原笔记涉及小程序类目、备案、模型接入限制、云开发套餐与模型价格的结论，都应在正式发布时依据官方最新规则核实。开发期的账单也不能直接代表多人使用后的成本。

## 4. 这两天最有价值的经验

### 真实课表才是解析器的规格

合并单元格、平日和周末不同时间、标题里的日期、姓名别称，这些细节才决定导入是否可用。用示例表格写出解析代码容易，用老师每天收到的真实课表跑通才有意义。

下一步可以保存一组脱敏样例：机构总表、个人分周表、合并时间块、没有日期的表、空表，以及重复导入的表。每次调整解析规则，都对照期望课程数量、日期和时间，避免修好一种格式后弄坏另一种。

### 数据“没了”，先看数据走到了哪里

原记录中的两个典型问题是：云函数写入缺少 `_openid`，以及客户端查询只取到了部分记录。它们提醒我，“导入成功”与“页面可见”之间还有身份、权限、查询和筛选几道关。

源码已加入用户归属字段和通用分页函数，但并非所有查询都使用它。排障信息应覆盖：解析多少条、跳过多少条、新增多少条、失败多少条、页面读到多少条。这样的数字能帮助定位问题，也能让使用者理解结果。

### AI 反馈的核心是事实边界

当前提示词要求保留结构、不新增事实、不改变评价倾向，数据库也保留原文与润色结果，这是值得继续坚持的设计。

下一步应强化教师确认：原文和润色版对照，结果可编辑，复制前由教师检查。如果原文没有作业、知识点或评价，模型不应替教师补写。专业术语也不应让家长更难理解。

### AI 编程需要清晰验收

WorkBuddy 能快速写页面和排错，但需求负责人仍要提供真实输入、说明期望输出，并验证完整流程。有效的协作不是只说“帮我做一个课表”，而是说清楚“这张表应提取哪些课，重复导入时应怎样，调课后统计怎样变化”。

## 5. 我对下一阶段的更多想法

### 第一优先级：让同事放心用

当前版本适合继续做个人试用。推广给同事前，我会先处理以下事项：

1. **移除源码中的模型凭证。** 当前模型配置存在硬编码密钥兜底。应迁移到云端环境变量，检查历史暴露范围并按情况轮换凭证；笔记与分享材料不包含密钥值。
2. **收紧清空数据的边界。** `clearData` 除当前用户记录外，还匹配没有 `_openid` 的记录。多人环境下，这可能清掉归属不明的历史数据。普通用户清理应只作用于自己的数据，无主记录交给单独的迁移流程处理。
3. **核查数据库和文件权限。** 客户端多处查询依赖数据库权限过滤，需要在云端确认规则，并用两个测试账号验证互相不可读取或删除数据。
4. **完善提醒去重。** 每次授权都会新增订阅记录，定时函数逐条处理，可能对同一用户同一天重复尝试发送。宜以“用户 + 日期”限制每日发送，并记录结果；本地 quota 不应被当作平台真实授权状态。
5. **补齐分页与时间口径。** 提醒当前固定读取部分用户和课程，课程详情也存在固定数量查询；应统一分页。提醒日期应明确使用北京时间，并核验定时器的实际时区。源码注释写 20:00，而配置写 23:00，也应统一。
6. **避免反馈版本错配。** 修改原文后，已有润色结果仍保留。应将其标为待更新或清空，避免保存和复制与当前原文不对应的结果。

这些是静态阅读发现的改进方向，尚未修改代码，也不代表线上已经发生问题。

### 第二优先级：把“排好的课”和“实际上过的课”分开

真实工作里会出现请假、补课、调课、代课和临时取消。只有星期模板和打卡，迟早会碰到表达不清的问题。

我建议逐步区分三个对象：固定课程模板、某日的授课安排、实际授课记录。模板回答“通常什么时候上”，安排回答“这次计划什么时候上”，记录回答“实际是否上、上了多久”。反馈最好关联到某一次授课。

例如原定周三 14:00 的课改到周五 16:00，应记录这一回的调整，保留历史反馈，也不会悄悄改变以后所有周三的课。统计则分别展示计划、已完成、取消、补课与待写反馈。先把这些关系讲清楚，再考虑工资核算或复杂报表。

### 第三优先级：让导入可以解释、可以纠正

未来的导入体验可以从“识别出多少门”升级为：

**识别 → 预览 → 修正 → 冲突检查 → 确认 → 查看批次结果。**

每条记录保留来源文件、工作表、单元格或图片识别来源，帮助追溯错在哪；时间重叠、缺失日期、结束早于开始的记录明确提示。重复导入、部分失败与重新尝试应有确定行为。

图片识别适合作为补充入口。对于有明确格式的 Excel，优先使用可解释的规则解析；不确定的内容交给用户确认。不要让模型的猜测静默变成正式课表。

## 6. 产品先往哪里长

我更建议先做“每天打开的教师工作台”：今天有什么课，哪些上完还没打卡，哪些还没反馈，明天是否有安排。少几个操作，比增加很多模块更容易形成习惯。

可以先邀请少量同事试用，观察两周：

- 导入时需要改多少条？哪些表格总失败？
- 老师每天是否打开课表，打卡是否能坚持？
- 一条反馈从写到确认复制实际需要多久？
- 月底统计与老师自己的记录差多少，原因是什么？
- 老师停止使用时，卡在授权、导入、调课还是反馈？

先收集这些结果，再决定要不要做机构后台、家长端或复杂管理权限。避免过早把个人效率工具变成全面的教务系统。

成本也应按真实使用量记录：一次导入、一次图片识别、一次润色、一次提醒分别花费多少。反馈和课表可能涉及学生信息，应尽量减少传给模型的身份信息，并明确文件保留、删除与数据导出方式。

## 7. 下一步行动清单

- [ ] 处理源码凭证、清理边界与双账号权限验证。
- [ ] 验证订阅提醒的授权、时区、分页、去重和真实送达。
- [ ] 给导入加脱敏样例、字段修正和冲突提示。
- [ ] 明确统计口径，处理原文修改后的润色状态。
- [ ] 用真实的调课、取消、补课场景检查数据结构。
- [ ] 邀请少量同事试用，记录失败与节省时间的数据。
- [ ] 发布前核实官方类目、备案、模型接入与实际费用。

两天完成的成果，是把一个反复发生的工作问题变成了可以操作的流程。下一阶段的价值，则是让它在不同老师、不同课表和各种临时变化里依然可靠。
